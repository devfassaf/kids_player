# v1.0.94 — the folders that were never backed up

**Field report (2026-10-05):** a folder of Drive lectures that had shown on a child's home
"disappeared this morning — from the home and from search — with no app update", while the
parent screen still listed its songs. The family uses the app on more than one device with
one Google account.

## What the parent was looking at

- **הוספה → "הסרטונים הקיימים"** grouped the songs under bare **"תיקיה (15)"**, **"תיקיה (20)"**
  sections. That bare title is what `plan.groupLibraryByFolder` gives a `cf:` folder id that
  has **no folder row**.
- **מקורות → "תיקיות"** showed no count: zero folder rows on the device.
- The child's home and search build folder tiles **from rows alone** (`app.buildFolders`), so
  751 approved songs were unreachable.

## Root cause — proven on the family's own backup

`drive.serializeDb` is the whitelist every push runs the local document through **before** it
merges or uploads (`pushDrive`: `parseDb(serializeDb(buildLocalDoc(...)))`). v1.0.56 added
parent-made folders to `buildLocalDoc`, `mergeDbFiles` and `applyRemoteDoc` — and never to
`serializeDb`. So from v1.0.56 on:

- every video travelled, each still naming its `cf:` folder;
- **no folder row and no folder tombstone ever reached Drive.**

The family's backup, downloaded twice, says exactly that:

| backup | videos in the library | Drive songs | folders they name | folder rows | folder tombstones |
|---|---|---|---|---|---|
| 2026-09-06 | 11,081 | 751 | 32 | **0** | 0 |
| 2026-10-05 | 14,741 | 751 | 32 | **0** | 0 |

The 751 songs were imported in one run on 2026-08-30 and never moved since. The rows lived
only on the device that imported them — so a restore, a second device, or that device losing
its local data all ended the same way: songs present, folders gone. **Nothing deleted the
folders; they were never anywhere else.** Two passages in CLAUDE.md claimed the opposite
("custom folders are serialized wholesale", "it travels in the Drive doc") — both corrected.

## Why three changes ship together

1. **Rows and tombstones travel** — `serializeDb` carries `customFolders` and
   `deletedCustomFolders`. A test pins the *shape*: every key `mergeDbFiles` emits per library
   must survive `serializeDb`, so the next collection cannot be forgotten silently.
2. **Placement is last-deliberate-placement-wins** (`placedAt`, `normalize.settlePlacement`,
   via `mergeVideoCopies` in both `mergeDbFiles` and `applyRemoteDoc`). Without it, change 1
   would have created the bug it fixes: `mergeVideoRecord` takes the folder from its survivor
   (the older copy; a tie keeps the local one), so a folder deleted on one device with "keep its
   videos" would send its **tombstone** to the others while their copies stayed filed under it.
   Narrow on purpose — when neither copy carries the stamp (every channel video), the merge is
   unchanged.
3. **A pull may not revert a newer row** (`drive.newerRemoteRows`, all three apply plans).
   `pullDrive` applies the raw remote document and the push is debounced, so a rename made just
   before a pull used to be reverted — harmless while folders never travelled, the next report
   once they do. A rebuilt placeholder never beats a real row.

## The repair — the family's folders come back on update

`app.repairOrphanFolders` (pure decision: `plan.planOrphanFolderRepair`) runs in the entry
refresh **after** the pull and the Drive refresh, **before** the empty-folder sweep:

- a folder whose row this device still holds under another scope → **adopted**, exactly;
- a folder that was **deleted** (tombstoned) → not resurrected; its songs go to
  "סרטונים נוספים", the delete dialog's default, stamped so it travels;
- a folder whose **every** video sits in the rejected archive → left alone (nothing in it can be
  shown); it comes back the moment one of them is restored;
- otherwise → a **placeholder under the ORIGINAL id**, named from its songs
  (`plan.placeholderFolderTitle`): no song is rewritten, and a real row from any device
  replaces the guess.

**A placeholder never leaves the device that rebuilt it** (`drive.travellingFolderRows`). An app
before v1.0.94 puts every remote folder row over its own, whatever its age — a device still
holding the real folder would have its name, tree and Drive link overwritten by the guess. Each
device rebuilds its own placeholder under the same id instead; the parent renaming it, or the
Drive link restoring it, makes it a real row, and only then does it travel.

It costs nothing when nothing changed: a scan that found nothing to repair is remembered
against `db.dataVersion()` (every committed write moves it, a pull's included), and the scan
itself is key-only on the `cf:` slice of `by_folder_sort` (the family has 14,000+ videos; this
runs on every home entry).

## Getting the real names and tree back

The placeholders carry names guessed from the songs ("סוד המיתה ועוד", "מגילת קהלת") and sit
flat on the home. **Pasting the Drive folder link again restores the original names and the
nested tree — in place.** A Drive folder the walk finds no row for BECOMES the placeholder that
holds most of its songs (`plan.pickPlaceholderToAdopt`; ties go to the smaller id so two devices
pick the same one). The placeholder already carries the folder's original id, so it is upgraded
where it stands — Drive name, place in the tree, Drive link — and **no song moves, nothing is
emptied, nothing is swept, no tombstone is written**.

The first version minted new rows, moved every song into them and swept the emptied
placeholders with tombstones. The review found what that costs: a device still holding the REAL
folder under that id, on an app that had not updated yet, would apply the tombstone and lose it.
Upgraded in place, the real row and the restored one are the same row, and last-writer-wins only
decides which name it carries.

Songs whose folder has **no row at all**, and — on a fresh paste only — songs in the loose list,
still move into the walked folder (`plan.refileEligible`, decided on the walk's snapshot and
re-checked inside the write). The 30-minute refresh adopts too, so a tree whose root row
survived heals without a re-paste. The outcome says "התיקיה שוחזרה! N קבצים חזרו למקומם"; a
placeholder's guessed name may not push the real name into "(2)". The parent's folder list
explains this next to every rebuilt folder.

## Every write is made against the record as it is now

Rows travel now, so a stale write is no longer a local glitch — it wins on every device:

- **Moves** go through `db.placeVideos`: the fields come from the ONE parking rule
  (`normalize.placeInto` — a pending or rejected video moves only its `homeFolderId`), computed
  from the record read inside the write transaction, with the caller's precondition re-checked
  there (`accept`). The re-file used to write whole snapshots back after the walk, stamped
  `placedAt: now`: a rejection that landed meanwhile could be reverted everywhere.
- **Folder rows** are patched on the live row (`db.updateCustomFolder`). The Drive refresh's
  stamp (`driveSyncedAt`) is written with `touch: false` — it is housekeeping, and stamping
  `updatedAt` for it let a refresh on one tablet beat a rename made on the other. It is also
  device-local: stripped from the document and kept on apply (`PER_DEVICE_FOLDER_FIELDS`).
- **A copy nobody placed never beats one somebody did.** `settlePlacement` used to let an
  unstamped copy compete with its `addedAt`, so a channel sync importing the same video later
  on another device pulled it out of the parent's folder. It competes as zero now.

## Mixing versions: safe, not tidy

A device still on ≤1.0.93 carries no folder rows in what it writes: a blind write of its own
drops every row and folder tombstone from the document until an updated device pushes them back,
and its merge of a moved song drops `placedAt`, so the document's copy flips between the two
devices until the old one updates. Nothing on an updated device is lost (absence is never a
deletion). The two paths that WOULD lose data are closed: a placeholder never reaches an old
device, and the restore writes no tombstone. **Update every device.**

## Also fixed

- `importDriveFolder`'s final root stamp wrote a snapshot taken before the network-bound walk
  (a lost update). It patches the live row now.
- The repair skips the scan while nothing has been written; a Drive walk loads the library
  once instead of twice; two rows naming one Drive folder are walked once per refresh; a fetched
  folder picture is no longer pinned in memory for the session.
- A folder picture reaches the other devices (`app.fetchFolderArt`, https-only, once per
  session) — the apply side's comment promised this fetch; nothing implemented it.
- A collection found by search said "0 סרטונים"; search entries carry `children` now.
- `localUsedAt` (the cache prune's clock) travelled in every backup — 13 records in the
  family's — because its guard banned the *word* from drive.js instead of checking the strip.

## Verification

- `test/folder-sync.test.mjs` (30) + 4 wiring guards + 4 reshaped; **64 planted regressions,
  every one red** (37 before the code review, 27 after; three of the guards were caught vacuous
  or mis-planted by the cycle and fixed — the last one, a ban on spreading named snapshots, is
  pinned by count now).
- **On the family's real backup**, in the browser, through the real `pullDrive` (stubbed token,
  nothing sent to Google): the exact reported state (751 songs, 32 row-less folders) → the entry
  refresh rebuilt all 32 on the child's home, searchable, with named library sections and the
  parent's note → a real push uploaded the 32 rows and no device-local stamps → re-pasting a
  served Drive tree built from the family's real song ids restored the nested tree with its
  Drive names. The family's data was removed from the dev environment afterwards.
- **The reviewed design, on a synthetic library of the same shape** (every Google request
  answered inside the page): the repair rebuilt three placeholders, skipped an all-rejected
  folder, sent a deleted folder's songs to the loose list, and still repaired an orphan written
  mid-session; push #1 uploaded no placeholder; the re-paste — through the real code gate and
  add form — answered "התיקיה שוחזרה! 11 קבצים חזרו למקומם (3 תיקיות) · נוסף קובץ חדש אחד" and
  upgraded the three placeholders in place (same ids, Drive names, nested, no song moved but the
  loose one, no tombstone, the refresh stamp not counted as an edit); push #2 carried the four
  real rows without the device-local stamp; a pull took a newer rename, kept the local stamp,
  and replaced a placeholder with an older real row; the 📁 move, a parked move, a refused
  precondition and "delete the folder, keep its videos" all behaved, with no console error.

## For the family, after updating

1. **Update every device**, and open the app on each one: the folders come back (named from
   their songs). If one device still holds the real folders, its update sends them to the
   others and they replace the guesses by themselves.
2. Optional — if the names are still guesses: parent screen → הוספה → paste the Drive folder
   link again. Do it on one device; the others follow.
3. From now on folders are in the Drive backup, so a restore or a new device brings them too.
